# Skill 09 · 上下文与 Token 效率

**何时用**：每个新会话开工前；长任务每 20~30 轮复盘一次；发现"读了又读、改了又错"时立刻启用。

**核心认知**：Token 效率不是"少问问题"，而是**让每一轮送进去的内容都与当前任务相关**。上下文同时决定**钱**和**质量**——脏上下文不仅贵，还会让模型判断力下降，进而引发更多试错，形成正反馈。

## 一、成本模型（先看机制，再看技巧）

三个乘数决定单轮成本：

| 因素 | 机制 | 对规范的含义 |
|---|---|---|
| 上下文体积 | 每轮重发"系统提示 + 工具定义 + 历史 + 文件读取 + 工具输出" | 控制体积是第一杠杆 |
| 输入 / 输出倍率 | 输出 token 约为输入的 5 倍 | 长文档、长解释比读文件更贵 |
| 缓存（prompt caching） | 命中读 0.1x，写入最高 2x；请求前缀逐字匹配才命中 | **别打掉缓存**比"少说两句"重要得多 |

**会打掉缓存的动作**：会话中途切模型 / effort、进入或退出 plan 模式、开启 fast mode、`/compact`、改动 MCP server 或工具定义、缓存过期（订阅制约 1 小时，API key 约 5 分钟）。

**结论**：所谓"历史越长越贵"在有缓存时并非线性成立——缓存命中的前缀只付 0.1x。真正的浪费是**频繁打掉缓存 + 把无关内容塞进上下文**。

## 二、五个杠杆（按投入产出排序）

### 1. 会话层：一任务一会话

- 一个会话只做一件连贯的事。**话题切换就换会话**：从 dsh-linkdog 跳到 dsh-linkdog-pet，从"写代码"跳到"部署排障"，都要换。
- 判断规则：**下一段提示放进全新终端也完全成立 → 现在就 `/clear`**；任务没完、必须保留上下文 → 用 `/compact`。
- 新会话第一句只给三样：**目标 + 交接文档路径 + 当前阻塞**。不复述历史，让新 Agent 去读文件。
- `/compact` 前先手写一张"未做事项清单"，压缩后逐条对照——压缩会丢细节，这是最大副作用。
- 趁缓存还热时 compact（休息前做），成本约为过期后做的 1/10。
- 走偏的最近几轮用 `/rewind` 退回，成本为零；`/compact` 要花钱。

### 2. 输入层：精准读，不 dump

- **给锚点，不要给范围**：指明"文件 + 函数 / 锚点"，让模型精准 edit，不用整文件读。
- `grep` / `Select-String` 先定位，再读关键 20 行；禁止用整文件读取代替搜索。
- 日志、命令输出**落到文件后搜关键词**，不把全量贴进会话。
- 报错只贴**关键 3~5 行 + 时间点**，不贴整段 traceback。
- 同一文件不重复读：已知内容不重读，不确定才读。
- 需要对比时**给参照物**（能用的那份配置 / 日志），比让模型猜便宜得多。
- 常驻开销要清理：不用的 MCP server 断开；大段项目说明从 `AGENTS.md` 移到 skill 按需加载。

### 3. 输出层：输出比输入贵 5 倍

- 改代码只输出**增量 diff + 文件路径 + 行号**，解释 ≤ 2 行（LinkDogDM `.trae/rules` 已有此约定）。
- 回答只给**结论 + 证据行**，不复述过程。
- 长文档**先给目录 / 要点**，人确认后再写全文。
- 长任务明确要求："每完成一个阶段简单总结变更点即可，不要主动扫描其他文件。"

### 4. 委派层：大搜索隔离到子 Agent

- 全仓搜索、批量阅读、日志分析 → 交子 Agent，只回传**路径 + 行号 + 结论**，主上下文几乎零增长。
- **不适合委派**的：需要人逐步拍板的开放性决策、需要边看边讨论的细活——来回追问会让总成本反升。
- 判据：范围独立、输出很多、最后只需摘要 → 委派；否则留在主会话。

### 5. 验证层：静态自检优先（与 skill 07 联动）

- 本地无依赖时先跑 `ast.parse` / `py_compile` / `node --check` / 渲染探针，再谈运行时验证。
- **失败就停，先报告**，不要连续试三种方案——每个错误假设都要带着膨胀的历史重跑一遍。
- 改完只在本地跑最小验证，不主动跑长测试。

## 三、该花的地方（不要为省而省）

| 值得花 | 原因 |
|---|---|
| 一次性读准关键文件（如定位到那 20 行） | 避免后续 3~5 轮猜测 |
| 写可复用资产（交接文档、协议文档） | 一次写入，后续每个会话省回来 |
| 一次决定性验证（`/state` 一行 JSON 证明链路通） | 顶十轮口头推断 |
| 开工前先规划、人确认方向 | 跑偏后全部上下文变沉没成本 |

**关键约束不能砍**：省 token 不是砍掉必要上下文。缺一条约束导致的反复试错，比多几百 token 贵得多。

## 四、可直接照做的提问模板

1. "**先只用一条命令确认**，再动手。"
2. "**只看关键 20 行**，不要 dump 全量。"
3. "改完**只在本地跑渲染探针**，不要长测试。"
4. "**不要重读已知内容**；不确定再读。"
5. "回答**只给结论 + 证据行**，不要复述过程。"
6. "长文档**先给目录 / 要点**，我确认后再写全文。"
7. "**失败就停，先报告**，不要连续试三种方案。"
8. "**A / B 你推荐哪个，一句话理由**"——决策题给选项，比开放式讨论省一半。

## 五、自检清单（收尾时过一遍）

- [ ] 这个会话只做了一件事？换话题是否已经 clear / 换会话？
- [ ] 有没有整文件读取本可以用 grep + 20 行解决？
- [ ] 有没有同一文件读了 3 次以上？
- [ ] 输出里有没有大段复述、整份日志、过长解释？
- [ ] 中介机构切换 / compact 的时机是否在缓存还热时？
- [ ] 交接文档是否已落盘，下个 Agent 能否不靠聊天记录恢复上下文？
- [ ] 关键约束有没有因为"省 token"被省掉？

## 反例（真实教训）

- 一个会话里同时做两个不相关项目 → 后半程每轮都在为前半程付费。
- 为了"看一眼"dump 整份日志 → 200 行日志进上下文，后续每轮都带着。
- 同一个错误假设反复验证 3 轮 → 应该先 diff 能用的版本。
- 中途切模型 / effort → 缓存全失效，整段历史按全价重新 prefill。
- `/compact` 前没列未做事项 → 压缩丢掉还没实施的方案，几小时后才发现。
- 长会话不检查点 → 自动压缩触发，细节丢失且无法回溯。
