# Skill 10 · AI Commit 评审与合并

**何时用**：AI 产出新 commit 后、合并进主线前；同步上游改动到本地时。

**一句话原则**：AI commit 是**不可信输入**，不是"已经写好的代码"。人在合并键上负责，AI 的自述不算证据。

---

## 1. 三条责任线

| 角色 | 负责 | 不算负责 |
|---|---|---|
| AI（产出） | 写代码 + 自校验 + 说清改了什么 | 判断"能不能合并" |
| 评审者（人或 AI 辅助） | 逐行看 diff、跑验证、给结论 | 替产出方辩护 |
| 人（最终） | 合并、推送、真机验收、上线 | 把 AI 的"已通过"当验收 |

> AI 说"我验证通过了"只代表它跑过命令，不代表合并安全。合并决定永远由人做。

---

## 2. Review 固定顺序（先看范围，再看细节）

顺序不能反——先 scope 能决定后面怎么读。

### 第 1 步：Scope（范围）

- 打开 diff，列出**所有**改动文件，和本次需求逐条对。
- 任何不在需求里的改动都要解释，解释不了就回退。
- 重点关注：依赖变动、配置改动、测试被删、批量改名、删"没用"的代码。

### 第 2 步：Intent（意图）

- 改动是否符合系统的设计约定（查 `AGENTS.md` 与《当前方案声明》）。
- 违反已写明的规则 → 直接打回，不用往下读。
- AI 常"补全"需求里没说的部分，看起来合理但违背架构——这是最贵的错。

### 第 3 步：Tests（测试）

- 新逻辑有没有测试？测试在证明行为，还是只让 CI 变绿？
- **反向验证**：故意把实现改坏一处，看测试是否变红。不变红的测试保护不了任何东西。
- AI 会写"迎合自己实现"的测试：代码错了，测试跟着错。需求驱动的用例比代码驱动的可靠。

### 第 4 步：Behavior（行为）

- 跑起来看：正常路径 + 边界（空 / 重复 / 超大 / 非法输入）+ 失败路径（超时 / 取消 / 部分完成）。
- diff 看不出 UI 塌陷、日志打码失效、真机动作对不上。这部分交给人（见 `skills/07` 三层验证）。

## 3. AI 特有红旗（看到就停）

| 红旗 | 为什么危险 | 动作 |
|---|---|---|
| 小任务大 diff | 顺手改了一堆无关代码 | 要求拆分，200 行能讲清就别给 2000 行 |
| 幻觉 API / 包 | 方法名、参数、依赖是编的，读起来很自然 | 查**实际使用版本**的官方文档 / 注册表，别信注释和自述 |
| 吞异常 / 静默兜底 | `catch` 里什么都不做，错误被默认值盖住 | 要求显式失败或记录 |
| 硬编码密钥 / 测试数据 | 密钥进代码，测试数据混进逻辑 | 按 `skills/08` 分层，一律打回 |
| "implement later" / TODO 占位 | 半成品冒充完成 | 要求补齐或明确标 WIP |
| 重复造轮子 | 新写 helper，忽略已有的 | 搜索同名 / 同义函数，能复用就复用 |
| 测试与代码同 PR 被改 | 削弱断言来"通过"测试 | 单独审查测试改动 |
| 作者讲不清 | 说不出某行为什么这么写 | **不合并讲不清的代码**（Simon Willison 规则） |

## 4. 合并决策表

| 场景 | 做法 | 理由 |
|---|---|---|
| 本地领先远端 1~2 个干净 commit | `git push`（fast-forward） | 最简单，无分叉 |
| 远端有新 commit，本地未提交 | `git pull --rebase` | 保持线性历史，不留合并噪音 |
| 本地有未提交改动且远端有更新 | **先 commit 或 stash，再 rebase** | 别让 rebase 吃掉工作区 |
| 只想要某个 commit，不要整条分支 | `git cherry-pick <hash>` | 精准摘取，避免带入无关改动 |
| 上游二开、双方都改同一批文件 | **不要自动 merge**，走 `skills/06` 功能级核对 | 文件相同 ≠ 功能一致 |
| diff 过大 / 讲不清 / 有未解冲突 | **拒绝合并**，退回拆分 | 宁可慢一轮，不埋雷 |

### 合并前必查（人执行）

- [ ] 每个 commit 都能单独说清做了什么
- [ ] CI 全绿（命名 / 链接 / 保护清单），且验证不是被跳过的
- [ ] `git status` 干净，没有未追踪的敏感文件
- [ ] 本地化配置 / 密钥 / 人设不在待提交列表（见 `skills/06` 保护清单）
- [ ] 真机项单独标注"待验收"，没被算进"已完成"

## 5. 冲突处理（三层优先级）

冲突时不要"谁新谁赢"，按这个优先级判断：

1. **保护清单优先**：本地化生产配置（MQTT IP、密钥、人设）、`config_secret.json`、自有资产（`scripts/agent-sdk/`、`调试记录/`、`.learnings/`）——**绝不覆盖**。
2. **当前方案声明优先**：查《当前方案声明》，落在废弃链路上的改动直接丢。
3. **功能级核对**：MD5 / 大小 / mtime 任一不同 → 拉 diff → 定位到函数 → 判断是否当前链路。未逐行确认的标 `⚠️ 待审查`。

> 交叉修改同一文件时，宁可停下来问，也不要"智能合并"——幽灵代码就是这么混进来的（`core_backup_20260902/` 含废弃方法，搜索命中误导判断，最终整体删除 204 文件）。

## 6. 记录责任（合并后）

合并完成的 commit message 或交接记录里写清：

```
reviewer: <人 / Agent>
ai_tool: <使用的工具 + 模型>
verified: <跑过的命令 + 结果>
not_verified: <待真机 / 待跨机同步>
```

目的：出问题时能定位到"谁看的、用什么看的、没看什么"。这是 OWASP 对 AI 辅助改动的要求：**可归属于一个对安全和可维护性负责的人**。

## 反例（本项目真实踩过）

- **只看行数判断功能更全** → 幽灵代码误导，删了 204 个文件。
- **AI 自述"已验证"被当成验收** → `config/logger.py` 的 async 化在真机崩，只能暂缓。
- **同步时本地化配置被上游覆盖** → MQTT IP / 天气 key / 人设丢失；现在明确"绝不覆盖"。
- **同一会话做两个项目** → 上下文串味，commit 描述混在一起，追溯困难。
